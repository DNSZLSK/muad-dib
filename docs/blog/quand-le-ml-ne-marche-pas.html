Quand le ML ne marche pas : pourquoi j'ai remplacé un classifier par des règles déterministes

2026-04-19
ml retrospective xgboost post-filtre méthodologie

Le 5 avril, j'ai publié un article qui annonçait FPR 11% à 2.85%, TPR 99.93%, AUC 0.999. Les chiffres étaient impressionnants. Ils étaient aussi faux.

Pas faux dans le sens "j'ai inventé des nombres". Faux dans le sens "le corpus de validation contenait 44 807 packages labellisés clean par le scanner lui-même, sans aucune review humaine". Le modèle apprenait à reproduire les décisions du scanner, pas à corriger ses faux positifs. AUC 0.999 sur ce corpus = AUC 0.999 pour deviner ce que le scanner avait déjà décidé.

Cette retrospective raconte les 24 heures où j'ai diagnostiqué le problème, tenté un retrain propre sur 302 labels humains, mesuré que XGBoost n'arrivait pas à exploiter les features sur ce corpus, et finalement remplacé le classifier par un post-filtre déterministe qui cape 67 FP sur 198 (33.8%) avec zero malware impacté. Le résultat est moins spectaculaire que les chiffres d'avril. Il a l'avantage d'être mesuré.

Le diagnostic de contamination

Tout part d'une review manuelle. La semaine du 10 au 18 avril, le moniteur a flaggé 2 146 packages avec un score ≥ 70. J'ai ouvert chaque tarball, lu le code, classé : malware ou faux positif. 5 jours, 8h par jour, l'équivalent d'une session forensique complète.

Le constat est net. 8 clusters de FP émergent :

  • Bundles minifiés sans aucun script lifecycle (babylonjs, vue.runtime.global.prod.js, electron)
  • Installers binaires depuis GitHub Releases (esbuild, swc, sharp, prebuild-install)
  • Endpoints réseau dans le scope du package (@stripe/stripe-js qui fetch api.stripe.com)
  • Git hooks écrits depuis source locale (husky, simple-git-hooks)
  • Typosquats sur noms scoped (faux trigger Levenshtein sur @scope/foo vs @scope/foobar)
  • Obfuscation commerciale (jscrambler, javascript-obfuscator) sans signal d'attaque
  • Placeholders anti-dep-confusion (index.js qui fait module.exports = {})
  • Install scripts sans network egress (config loaders, build scripts pures)

Bonus de la review : 2 vrais malwares étaient passés en zone P3 jaune et n'avaient pas été ouverts (percy-cake-docker, renovate-config-doctolib). Si un humain ne les avait pas pris au hasard, ils restaient invisibles.

Sortie de la review : un corpus humain de 302 packages, tous labellisés à la main : 198 FP confirmés + 104 malware confirmés. C'est ce corpus qui sert de référence pour la suite.

Les 8 features F1-F8 (v2.10.96)

Plutôt que d'ajouter encore 8 heuristiques au scanner (qui finiraient par tirer aussi sur des malwares qui imitent ces patterns), je construis 8 features contextuelles dans src/ml/feature-extractor.js. Chaque feature est un boolean, chacune cible un cluster :

IDFeatureCluster
F1bundle_without_install_scriptsBundles minifiés sans lifecycle
F2install_url_github_releasesBinaires depuis GitHub Releases
F3network_destination_first_partyRéseau dans le scope du package
F4git_hook_source_localGit hooks locaux
F5typosquat_scoped_packageFaux trigger Levenshtein scoped
F6obfuscation_without_vectorObfuscation commerciale
F7placeholder_anti_dep_confusionPlaceholder dependency confusion
F8install_script_no_network_egressInstall sans egress réseau (DESACTIVEE)

F8 est laissée inerte (features.install_script_no_network_egress = 0). En la mesurant sur le corpus malveillant, je vois qu'elle classifie 19 malwares comme FP : ils exfiltrent via dangerous_exec (curl/wget direct), pas via les types réseau Node.js trackés par EGRESS_TYPES. Si je l'active, le ML retrain apprend "install_script_no_network_egress = benign" sur des malwares confirmés. Mieux vaut une feature inerte qu'une feature qui pollue.

La plomberie suit : homepage extrait de npm-registry.js (nécessaire pour F3), threat.urls[] ajouté dans handle-post-walk.js (host extrait de chaque URL détectée), fileSizes propagé jusqu'au build du record ML. Aucun changement de scoring : v2.10.96 produit les mêmes scores que v2.10.95 sur tous les packages. C'est de la pure plomberie pour ouvrir la voie au retrain.

Gate AUC FAIL : 0/8 features atteignent 0.70. Premier instinct : virer toutes les features et laisser tomber.

Sauf qu'en regardant la matrice de confusion par feature, la précision est 100% sur F1 à F6. Quand elles fire, c'est toujours un FP, jamais un malware. Le 0% de malware impacté n'est pas approximé : zéro, mesuré.

Comment réconcilier précision 100% et AUC ~0.55 ? C'est un piège classique des features binaires sparses. AUC mesure le ranking de l'ensemble du corpus. Une feature qui tire sur 35 packages sur 302 (cas de F1) a un AUC max théorique d'environ 0.61, même avec précision parfaite, parce que les 267 autres packages sont rankés au hasard. La métrique AUC est inappropriée pour évaluer un signal binaire qui ne s'applique qu'à un sous-ensemble.

Lecture honnête : ces features ne sont pas faites pour être discriminantes sur tout le corpus. Elles sont faites pour être déterministes sur leur sous-ensemble. AUC n'est pas la bonne métrique. Précision conditionnelle l'est.

Le retrain XGBoost à AUC 0.9998 suspect

Première tentative de retrain pour activer un classifier ML. Inputs : les 96 features (96 = 88 originales + 8 nouvelles F1-F8). Le corpus d'entraînement combine les 302 labels humains plus ml-training-merged.jsonl qui contient 44 807 records labellisés clean automatiquement par le moniteur.

Résultats :

MétriqueValeur
AUC holdout0.9998
TPR @ 1% FPR1.0
Precision1.0
Recall1.0

Trop beau. Quand un modèle atteint precision 1.0 et recall 1.0 sur du data réel, c'est presque toujours du data leakage.

Diagnostic : le modèle n'apprend pas à distinguer FP de malware. Il apprend à distinguer "scanné clean par le scanner" (44 807 labels auto) de "malware connu". Le signal vient des labels auto pollués. C'est exactement la même erreur que celle documentée dans l'article du 22 mars, mais plus subtile : cette fois le pipeline n'utilisait pas directement les labels fp, il utilisait des labels clean du scanner. Variante du même piège.

Règle violée : ml-training*.jsonl est un fichier de dédup référentiel, jamais une source de labels. Le retrain est rejeté.

Le retrain propre sur 302 labels humains

Deuxième tentative. Corpus humain uniquement : 198 FP + 104 malware = 302 samples. Stratification 80/20, holdout 60 packages, 5-fold cross validation.

Écart AUC holdout vs CV inférieur à 0.003. Pas d'overfitting. Le modèle est honnête.

F1 (bundle_without_install_scripts) arrive en rang 3 du feature importance avec 0.1149. Les autres features F2-F8 ont une importance proche de zéro.

Les features F1-F8 ont importance 0 dans XGBoost

Top 5 features du modèle retrainé :

  1. file_count_total
  2. count_low
  3. dep_count
  4. type_dangerous_exec
  5. type_crypto_decipher

Les features que j'avais soigneusement construites pour cibler les 8 clusters de FP : importance 0. Comment c'est possible alors qu'elles ont précision 100% sur leur sous-ensemble ?

Réponse de manuel XGBoost. Sur 302 samples, le modèle préfère splitter sur des features continues qui partitionnent 100% du corpus (file_count_total divise 302 en 2 groupes équilibrés à chaque split) plutôt que sur des features binaires sparses qui ne discriminent que sur 14% du corpus (F1 ne tire que sur 42 packages). Le gain d'information par split est plus grand sur les features continues, même si le gain final sur les FP est plus petit.

Conclusion : XGBoost sur 302 samples ne peut pas exploiter des switchs binaires sparses. Il faudrait probablement 2 000+ samples avec une meilleure couverture par cluster pour que les F1-F8 émergent dans le ranking. La théorie le sait depuis longtemps, j'avais besoin de le mesurer pour le voir.

Le pivot vers post-filtre déterministe (v2.10.97)

Constat : les 7 features actives (F1-F6 + F7) ont précision 100% sur leur sous-ensemble. Ce n'est pas un signal probabiliste qu'un classifier doit apprendre à pondérer. C'est un signal déterministe. XGBoost est inutile. Un post-filtre de règles est plus approprié.

Implémentation : applyContextualFPCaps() dans src/scoring.js. Sept caps déterministes branchés sur les helpers de feature-extractor.js. Appliqué APRES calculateRiskScore, donc les compound boosts et les lifecycle floors ont déjà eu le dernier mot.

CodeCapJustification
F130Bundle minifié sans lifecycle = bibliothèque, pas un dropper
F235Installer binaire depuis GitHub Releases = pattern légitime
F330Endpoint réseau dans le scope du package
F435Git hooks écrits depuis source locale
F5--Soustrait les points typosquat (pas un cap)

Quand plusieurs caps s'appliquent, le Math.min() gagne (cap le plus serré). F5 est traité séparément : il soustrait les points typosquat au score au lieu de plafonner.

La leçon méthodologique

Cinq points qui valent la peine d'être notés.

1. AUC 0.999 sur petit dataset avec sources mixtes = data leakage presque garanti. L'article du 5 avril est un cas d'école. Le vrai AUC sur corpus humain propre est 0.9917. La différence de 0.008 paraît minime, mais elle cache le fait que le 0.999 venait du modèle apprenant à reconnaître la source des labels, pas le contenu des packages.

2. Un sandbox sans honey tokens qui labellise fp automatiquement = label poisoning sur soi-même. C'était la leçon de mars 2026 (article ml-audit-fondamental). Le retrain d'avril a re-rencontré le même piège, déguisé en utilisation des labels clean du moniteur au lieu des labels fp. La règle ml-training*.jsonl = dédup référentiel, jamais source de labels mérite d'être imprimée et collée au mur.

3. XGBoost sur petit corpus (< 1000 samples) ne peut pas exploiter des features binaires qui tirent sur < 15% des samples. Le modèle préfère systématiquement splitter sur des continues qui partitionnent l'ensemble. Pour que des features sparses émergent, il faut soit beaucoup plus de données, soit changer d'approche.

4. Une feature à précision 100% sur son sous-ensemble est un signal déterministe, pas probabiliste. Un post-filtre de règles est plus approprié qu'un classifier dans ce cas. C'est moins glamour qu'un modèle ML, c'est plus simple à debugger, et chaque cap est explicable individuellement à un humain.

5. Valider sur le corpus malveillant aussi, pas seulement sur le corpus FP. F8 aurait été catastrophique si activée : elle classifiait 19 malwares comme FP. Mesurer uniquement sur le corpus de validation FP n'aurait rien révélé. La mesure croisée sur le corpus malveillant a fait gagner une régression silencieuse.

Ce qui reste

Le ML shadow model actuel tourne toujours sur le moniteur, mais le retrain n'est pas activé. Le post-filtre F1-F7 est en prod depuis v2.10.97. F8 sera réactivée après fix de EGRESS_TYPES (ajouter dangerous_exec, lifecycle_dangerous_exec, node_inline_exec, child_process).

Le retrain ML est reporté à quand le corpus humain atteindra 2 000+ labels. Rythme réaliste de review manuelle : 150-200 packages par session VPS. Donc 5 à 10 sessions pour atteindre la masse critique. Le ML reviendra quand les données le permettront.

Les chiffres annoncés dans les articles ML précédents (20-22 mars, 5 avril) étaient optimistes. Les vrais chiffres sur corpus propre sont AUC 0.9917, CV 0.9888 ± 0.0041, 67 FP cappés sur 198 (33.8%), 0 malware impacté. C'est moins spectaculaire, c'est mesurable, et c'est ce qui tourne en prod.

Un post-filtre déterministe vaut mieux qu'un ML instable sur petit corpus. Le ML reviendra quand les données le permettront, pas avant.
